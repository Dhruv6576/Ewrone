
Turf Booking Platform — Production Architecture and Implementation Plan
Architecture baseline: Supabase + Flutter + Next.js/React
Documentation checked: 17 September 2026
Purpose: An implementation specification for a real multi-tenant booking business.
Core recommendation: Build one shared, tenant-aware backend. Treat the Master Owner’s business account as the tenant, a turf as a managed venue, and a resource as the actual bookable ground/court. Employees receive explicit permissions on assigned turfs. Booking inventory, financial state transitions, and authorization must be enforced in Postgres—not in the applications.
The SQL below defines the core schema and security patterns. The workflow specifications describe the stored procedures, Edge Functions, tests, and operational controls developers must implement around it. This is a design document, not a claim that the migrations have been executed or security-audited.

A Master Owner record represents the business account, not merely a different kind of Auth user.
A turf represents a venue. A resource represents exclusive inventory.
For a simple venue with one ground, create one default resource. This adds little UI complexity while avoiding a future inventory migration.

Why not put all logic in Next.js?
The mobile applications need exactly the same business rules. A Next.js-only implementation tends to create separate mobile APIs and inconsistent authorization.
Next.js route handlers can act as thin web-specific adapters, but they must not become a second source of truth.
Why not put everything in Edge Functions?
Edge Functions are appropriate for network calls, webhook validation, and orchestration. They do not make several independent Data API calls atomic.
Transactions belong in one Postgres routine. External network calls belong outside that transaction.

For Next.js, use the current @supabase/ssr integration and server-side verified authentication. Do not trust the user object from an unverified session cookie. Follow Supabase’s current SSR guidance for token refresh and verified claims. [S3]
For Flutter, configure secure session persistence using OS-backed secure storage for sensitive tokens. Do not assume ordinary preference storage is appropriate.
One Auth project does not automatically mean one shared browser session across all websites. Prefer isolated host-scoped sessions, especially for admin. Do not place a shared parent-domain authentication cookie across public and privileged sites merely for convenience.

4.3 Permission evaluation
For turf-scoped operations:
ALLOW only when:
user is the active Master Owner of this turf's business
OR
employee membership is active
    AND membership belongs to this turf's business
    AND assignment to this exact turf is active
    AND assignment grants the requested capability
Platform administration is a separate path. Do not silently make every admin pass every owner permission helper.
For owner-account financial access, use separate explicit account grants. A turf assignment alone must never reveal consolidated revenue from unassigned turfs.
4.4 Employee invitation lifecycle
Step
Action
1
Master Owner enters employee email, assignments, and permissions
2
DB creates a pending invitation tied to that business
3
Edge Function sends an invite or acceptance link
4
Employee authenticates and accepts using a verified identity
5
DB verifies invitation expiry, recipient, and requesting business
6
DB creates/activates membership and assignments atomically
7
Audit records the inviter, recipient, and grants
Do not assign permissions merely because a caller supplies an email address or user_id.
Do not create employee accounts with shared passwords.
Disabling an employee should revoke the membership immediately for new database requests without disabling their unrelated player account.

6.2 Turf capability helper
A private SECURITY DEFINER helper can avoid recursive RLS joins into membership tables.
create or replace function private.can_turf(
  p_turf_id uuid,
  p_capability text
)
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select exists (
    select 1
    from public.turfs t
    join public.master_owners mo
      on mo.id = t.master_owner_id
    where t.id = p_turf_id
      and mo.status = 'active'
      and exists (
        select 1
        from private.capabilities c
        where c.code = p_capability
          and c.scope = 'turf'
      )
      and (
        mo.owner_user_id = (select auth.uid())
        or exists (
          select 1
          from public.employees e
          join public.employee_turf_assignments a
            on a.employee_id = e.id
           and a.master_owner_id = e.master_owner_id
          join private.assignment_grants g
            on g.assignment_id = a.id
          where e.user_id = (select auth.uid())
            and e.master_owner_id = t.master_owner_id
            and e.status = 'active'
            and a.active
            and a.turf_id = t.id
            and g.capability = p_capability
        )
      )
  );
$$;
revoke all on function private.can_turf(uuid, text) from public;
grant usage on schema private to authenticated;
grant execute on function private.can_turf(uuid, text)
  to authenticated;
Granting schema USAGE does not itself grant table access. Keep private table privileges revoked, and keep private unexposed through the Data API.
The function must be owned by a controlled migration/function-owner role capable of reading the membership records. Never let application users alter it.
Use a separate helper for owner-account reads, a separate onboarding authorization path, and separate admin capability checks.
The example intentionally requires an active business for normal turf operations. Owners in onboarding/suspension still need narrowly authorized account, support, and historical financial access.

7. Double-booking prevention and booking transactions
7.1 Why a unique slot ID is insufficient
Suppose one user requests 18:00–19:00 and another requests 18:30–19:30.
A uniqueness check on (resource_id, starts_at) would allow both.
The exclusion constraint checks the entire time interval, so any overlap is rejected.
Adjacent intervals remain valid:
18:00–19:00
19:00–20:00
7.2 Locking strategy
For MVP, serialize inventory-changing transactions by locking the resource row.
select id
from public.resources
where id = p_resource_id
for update;
This is intentionally simple.
The lock lasts only for a short database transaction—not throughout checkout.
All routines that hold, confirm, expire, block, cancel, or reschedule inventory must follow the same locking convention.
The exclusion constraint remains the final protection even if a future code path misses the lock.

7.6 Walk-in bookings
Walk-ins must use the same allocation table and exclusion constraint.
An employee must not create an offline booking in a separate table that bypasses online inventory.
Offline cash recording is a separate financial event. It must not be represented as a captured gateway payment.

10. Webhook ingestion, idempotency, and recovery
10.1 Webhook endpoint
A payment provider does not send a Supabase user JWT.
Configure the webhook endpoint accordingly, but replace user JWT authentication with strict gateway signature verification—not an unauthenticated business mutation path.
For Razorpay, signature verification uses the raw request body, and webhook delivery order is not guaranteed. [S6]

10.4 External-call uncertainty
A database transaction cannot atomically commit with a gateway API call.
For each outbound operation:
persist durable intent
commit
perform provider call
persist known result
If the network fails after the provider accepted the call:
mark operation unknown
query provider using stored identifiers
retry only after resolving uncertainty
Use provider idempotency only where that specific endpoint documents support. Do not assume all payment, order, transfer, and refund endpoints share the same idempotency mechanism.
An application idempotency key prevents duplicate local requests but cannot, by itself, prevent duplicate external side effects after an ambiguous timeout.

For private Broadcast channels, implement policies on realtime.messages and configure the client channel as private. Supabase documents that channel authorization is cached and refreshed on join/new JWT rather than checked for every message. [S2]

18.3 Database transactions and pooling
An RPC call is a transaction. Five sequential SDK calls are five separate transactions.
Do not attempt to issue BEGIN through one REST request and COMMIT through another.
If a function uses a direct pooled Postgres connection, do not rely on session-local settings persisting across unrelated requests. Use transaction-local settings.

18.5 Timezones
Store UTC instants and the venue’s IANA timezone.
Operating schedules and pricing rules use venue-local wall time. Booking inventory uses absolute instants.
Do not store 7 PM as the booking time. Do not use the player phone’s timezone to interpret a venue’s schedule.
Even if the initial market has no daylight-saving transitions, the data model should not depend on that assumption.
18.6 Soft deletion and historical ownership
A turf with bookings or money history cannot simply be deleted.
Remove turf should normally mean archive/unpublish after handling future bookings and pending funds.
Changing a turf’s master_owner_id is not an ordinary edit. It affects employee access, contracts, settlement destinations, and historical reporting.
For launch, prohibit self-service ownership transfer. Use a reviewed administrative workflow later.

18.8 Availability abuse
Attackers can repeatedly create holds without paying.
Use per-user and per-resource hold limits, rate limits, short TTLs, verified contact requirements, and risk-based abuse controls.
A queue of fake holds is a business availability incident even when the database correctly prevents double-booking.

19.3 Backup and recovery

Database recovery alone is not enough: the gateway may have processed payments while the database was unavailable or before a restored snapshot.
After a restore, run a financial reconciliation over the affected time window before resuming unrestricted settlement automation.
Maintain runbooks for booking holds stuck open, captured-but-unconfirmed payments, missing webhook events, refund uncertainty, and incorrect owner destinations.

Final recommendation
Build the backend around these four boundaries:
Boundary
Rule
Ownership
Master Owner business account owns the turfs
Authority
Employee access is explicit per turf and capability
Inventory
Postgres alone decides whether time can be reserved
Money
Verified provider events and an immutable ledger determine financial truth
Keep multi-turf ownership, employee assignments, database-enforced inventory, audit, and payment reconciliation in Phase 1. Trim advanced dashboards, reviews, complex rescheduling, and promotional features instead.
The most expensive mistakes in this product are not choosing the wrong UI library. They are allowing a staff member to cross tenant boundaries, confirming a booking without safe inventory, paying an owner twice, or losing track of a captured payment. This architecture puts those risks behind explicit database constraints, transactional workflows, and auditable recovery paths.
